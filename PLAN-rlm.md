# RLM implementation plan

Status: implemented.

Spec: `SPEC-rlm.md`. Base contract: `SPEC.md`.

## 1. Configuration

- `config.toml.example` and `src/config.rs`: required `[rlm] max_depth` (integer ≥ 1), `[rlm.store] path` (absolute path to an existing directory, opened at startup), optional `[rlm] subagent_prompt` (system message for subagents, replacing `[chat] prompt` for them, sent verbatim, an empty string included). Missing or invalid values are startup errors.
- No startup check that the harness directory lies outside the repository.

## 2. Session tree

- `src/session.rs`: a new root session is `sessions/<name>/library/root.json`, created at its first save. Branch files are `sessions/<name>/library/<call-id>.json` at depth 1 and `sessions/<name>/deep/<call-id>.json` at depth 2 and deeper. `list` returns the names of directories under `sessions/` that hold `library/root.json`, oldest first by its mtime; directories without it are skipped. `resume` loads `library/root.json` and rejects one recording a depth other than 0 or a `parent`. `Session::branch` rejects an ID not in the encoded call-ID format. `rename` renames the tree directory and refuses an existing destination.
- `LocalMetadata` has required `repository: String` and `depth: u32`, and `parent: Option<String>` (absent at depth 0). Set at creation, never rewritten. `turn_token_cache` is optional. The root records `depth` 0. `repository` is the canonical launch directory of the process that creates the session; resume does not compare it. `parent` is `root` for a depth 1 branch and the parent's call ID deeper.
- Unanswered `rlm` calls found on resume receive `[not run: turn stopped]` like any call.

## 3. Agents

- `src/agent.rs`: `Agent` owns a `Session`, `Turn`, `Phase`, tool set, REPL handle, the library it was given, and the latest `prompt_tokens`/`context_tokens` usage; its depth is its session's recorded depth. It runs the turn: `advance`, `start_request`, `on_stream`, `end_stream`, `save_reply`, `begin_call`, `run_call`, `on_repl`, `record_result`, `stop_turn`, and `next_turn_event`. Display-only notes and the failure log stay in the App; the agent reports failure facts and the App records them with `session` set to the tree directory name for the root and the call ID for a branch. Agent methods receive the App's shared resources (`Resources`: settings, HTTP client, REPL runtime, direct-tool runtimes) per call and return outcomes the App acts on (`Outcome`: start a branch, a REPL failure, a stream error); the App takes a branch's result from `answer`, or, when it stops or fails, the text ahead of its marker from `partial_content`. The App never changes an agent's `Phase` directly.
- `App` holds the agents as a stack: the root, then each active branch above its parent. Exactly one agent is active at a time, and the select loop awaits its events. The transcript, context overlay, token counter, and status line follow the top of the stack; the status line names the agent on screen: the session name (the tree directory name, following `/rename`) for the root, the caller-given `name` for a branch. The context overlay's header, expanded or collapsed, names every agent on the stack by the same rule, root first, as `[Context][<root>]…[<on-screen agent>]`, and when the nine-sixteenths width cap binds, the oldest ancestors after `[Context]` collapse into one `[…]` segment, the on-screen agent's name shortening with `clip_line`'s ellipsis only if it alone still does not fit. `/tools` shows the tools of the agent on screen. Only completed turns are tokenized and a branch's one turn is active whenever it is on screen, so branch files get no token cache. Each agent's `FYI` reports its own latest usage by the `FYI()` rule. The active agent's pending prompt is the approval prompt; `y`/`n` answer it. `--system-prompt` replaces `[chat] prompt` for every agent; `[rlm] subagent_prompt`, when set, replaces it for subagents. The transcript shows the on-screen agent's effective system message.
- `src/client.rs`: `tool_definitions(depth, max_depth, repl_description, mounts)`, built once per agent: depth 0 is `[rlm, FYI]`; depths 1 through `max_depth - 1` are `[REPL, apply_patch, read_file, grep, list, rlm]`; `max_depth` omits `rlm`. `rlm` has required strings `task` and `name`; a missing or non-string `name` gets the same malformed-arguments error as `task`. The name is persisted only in the parent's saved call arguments and held by the App for display; call IDs remain the branch identity for files, `parent`, and the failure log. `FYI` has no parameters and returns the `Date`, `Prompt tokens`, and `Model` lines the REPL host function prints. The `task` property's description is `The task for the subagent.`; the `name` property's is `A short (3-5 word) name for this subagent, shown to the user.` A call to a tool outside the agent's tool definitions returns `Unknown tool: <name>`, or, without executing anything, `Unknown tool: <name>. <name> is a REPL function, not a tool; call it inside REPL code: <signature>` when the agent has a REPL and the name is a host function with its mounts (`host::is_host_function`) or a helper function loaded in its turn's REPL (`Repl::helper_signature`), `<signature>` being a host function's help() stub line without its `: ...` body or a helper's help() signature line (`host::helper_signature`).
  - `rlm` at depth 1 through `max_depth - 1`, verbatim: `Delegate a task to a subagent.`
  - `rlm` at the root: the preamble `Delegate a task to a subagent and return its final answer. The subagent sees only your task text and works on the same repository with the following tools:` followed by one `name: description` entry per depth 1 tool, rendered from the depth 1 tool definitions so the two cannot differ. Entries are separated by blank lines. The depth 1 `rlm` entry, present when `max_depth` ≥ 2, therefore reads `rlm: Delegate a task to a subagent.` After the entries, separated by a blank line, the description closes verbatim: `These tools are available only to the subagent, not to you. You cannot call them directly.`
  - No description mentions depth, the depth limit, or the tree.
  - `FYI`, verbatim: `Report the current date, the prompt-token count of the latest request, and the model name.`
- Turn start: each turn opens with synthetic calls saved in one assistant message, all with the synthetic ID kind, run in order before the first request. At the root, one `FYI` tool call; in a branch, separate `FYI()`, `help()`, and `store_summary()` REPL calls, then `library_summary()` where `/library` is mounted. The per-turn cleanup removes earlier `FYI` tool calls alongside REPL calls made only of `FYI()`/`help()`.
- `rlm` handling in `begin_call`: `rlm` calls run in the ordered queue like every other call; every `rlm` call in a response runs, one at a time. Invalid arguments record `Invalid rlm arguments: <error>`. An accepted call puts the parent in `Phase::Delegating` and returns `Outcome::StartBranch`; the App creates the branch session file with the task as its user message, pushes the branch agent onto the stack, and opens its turn with its synthetic turn-start calls queued. When the branch session can't be created, the parent's result is `[branch failed: <error>]`. The parent waits until the branch ends.
- Branch completion: the final response content becomes the `rlm` result, recorded in the parent in call order and capped at the parent's output limit; empty content records `(no output)`. The branch is popped and the parent's `advance` continues. A branch that fails, by stream error or any other error, ends its turn the way a stream error ends the root's: its file keeps the partial reply, calls that never ran get `[not run: turn stopped]`, and the error is not stored in it. The branch returns the text streamed so far in its failed response followed by `[branch failed: <error>]` on its own line. A save error while ending the failed branch's turn still gives the parent the branch's captured text followed by `[branch failed: <original failure>]`, then ends the app through the normal stop path.
- Esc and exit stop every agent from the top of the stack down. The deepest agent records its stop as any stopped turn does. In every agent, calls that never ran get `[not run: turn stopped]`. The deepest agent's partial response followed by `[stopped by user]` on its own line becomes its parent's `rlm` result and passes up unchanged as each ancestor's `rlm` result to the root.
- A branch stopped or failed after its final response has fully streamed (while its REPL worker is returned, or when returning it or saving the response fails) passes that complete content followed by its marker.
- `/rename` while a branch runs shows `couldn't rename: a subagent is running` and keeps the input, like other rename refusals.
- `/new` (alias `/clear`) while any turn on the stack runs shows `turn in progress (esc to stop)` and keeps the input; otherwise it replaces the stack with a new root session.

## 4. REPL mounts and permissions

- `src/repl.rs`: `Pool` `max_processes = max_depth`: each waiting parent keeps its turn's checkout. `Runtime` opens the store once at startup as `MountSpec` `/store` read-write and as the directory capability `store_summary()` reads. `Runtime::start(depth, library)` takes the agent's optional library, supplied at depth 2 and deeper. Each feed passes the repository mount first, at `/repository`, then `/store` from depth 1 and `/library` read-only where the library was supplied.
- `src/root.rs`: `Library`, the `/library` mount and directory capability of `sessions/<name>/library/`, belongs to the App per tree: opened on first use, dropped by `/rename` and `/new` so the next use reopens the current tree's directory, and cloned into each agent created at depth 2 and deeper. The agent passes it to `Runtime::start` and to the direct tools per call (`Access::Library`); the direct-tool runtimes hold only the repository and store capabilities.
- `src/hostfs.rs`: `authorize` resolves by the root of the mount serving the path (longest virtual-path prefix among the feed's mounts), for REPL filesystem calls and the mount summaries alike. Under `/repository`: the current permission level. Under `/store`: allowed. Under `/library`: reads allowed, writes denied. Anywhere else: denied. Rename authorizes each endpoint in its own root; Monty's mount table rejects cross-mount renames.
- `src/host.rs`: `Mounts::at(depth, library)` fixes an agent's mounts; its feeds, `authorize`, `help()`, host-function lookup, tool definitions, and direct-tool roots all follow it. `help()` prints the output limit and `repl-notes.md`, then `Files:` (the repository with its live permission level, and each mount present with its mode and a short instruction: `/store` is a shared knowledge base and how to use it; `/library` holds session transcripts available to inspect), `Python:` (the supported subset and what to use instead), `REPL functions` (the host-function stubs), `Commands:` (`run()`'s contract and the allowed and denied names), and `Helper functions:` (loaded `replib` signatures and docstrings). `src/unsupported.rs` holds the one table of unsupported names, each with its alternative and exact Monty exceptions: `help()` generates `Python:`'s `Use instead` lines from it (`unsupported::help_lines`), and `src/repl.rs` adds `<name> is not available in this REPL; use <alternative>.` after a call's final exception when the table lists that exception (`unsupported::pointer`). Agents are told no IDs and no depth, and the text mentions neither depth nor the tree. `store_summary()` and `library_summary()` print their mount's regular-file count, total bytes, last update, and up to 5 most recently changed paths (`<mount>: empty` without regular files); each exists, and `help()` lists it, only where its mount is.

## 5. Direct tools

- `read_file`, `grep`, `list`, `apply_patch` arguments take optional `root` with values `repository` (default; omitted or null), `store`, `library`. Repository access follows the permission flags. Store access is always allowed. Library access is read-only; `apply_patch` with `root = "library"` from an agent that has the library returns `Not applied: root "library" is read-only`. Each depth's definitions offer only its roots; `library` appears from depth 2. `apply_patch` is offered only the writable roots (`repository`, `store`), never `library`. A call naming a root the agent lacks returns `<tool>: root "<name>" is not available`.
- Tool descriptions document `root`. The transcript and context overlay show `read_file`, `grep`, `list`, `rlm`, and `FYI` argument objects raw. `apply_patch` displays its patch text, preceded by a `root: <value>` line when its arguments include `root`; calls without `root` display only the patch.

## Known issues outside this plan

- `src/session.rs:216`: an entry with both `role` and `_harness_local` decodes as a provider message, and `_harness_local` is sent to the provider through `Message.extra`.
- `src/session.rs:612-617`: `rename` checks that the destination is absent, then renames in a separate step.
- `src/session.rs:401`: session names have one-second resolution; two sessions started in the same second (two launches, or a launch and `/new`) share a name.
